

## Project: CloudLite: Lightweight Self-Hosted Cloud Storage (Nextcloud/Seafile Alternative)
### Overview
A minimal, high-performance self-hosted file storage service built with Spring Boot.
The system focuses on:
- fast upload and download of many small files
- self-hosted architecture
- low operational overhead
It intentionally avoids the complexity and overhead of systems like Nextcloud, while learning from their bottlenecks.
### Core Design Principles
- Database (Postgres) is the source of truth for metadata
- Filesystem stores file content at user-prefixed real paths
- Files are stored under `<storage-root>/<user-sub>/<folder path>/<filename>`
- Directory structure is stored in the database
- Uploads are optimized for direct mapped batches
- Minimal synchronous work on upload path
- Everything else is asynchronous
### Functional Requirements
#### 1. File & Folder Management
- Create, rename, move, delete files and folders
- Hierarchical directory structure
- Unique filename constraint per directory
- Soft delete (optional trash support)
#### 2. File Upload
- Upload single files
- Upload many files efficiently via direct mapped batch upload
- Support large and small files
- Streaming upload (no full buffering in memory)
- Compute file size and checksum (SHA-256) during upload
#### 3. Batch Uploads (Critical Feature)
- Upload multiple files in one multipart request
- Provide a mapping from client-generated file IDs to destination folder paths
- Validate all folder paths and filename conflicts before streaming file bytes
- Stream each file directly to its final user-prefixed filesystem path
- Batch insert metadata after successful filesystem writes
#### 4. File Download
- Download full files
- Support HTTP range requests (partial downloads / streaming)
#### 6. Metadata Storage
Stored in Postgres:
- directory structure (parent_id tree)
- filenames
- ownership
- timestamps
- filesystem storage path
- file size
- checksum (SHA-256)
#### 7. Filesystem Storage
- Store file content at the same path represented by folder metadata
- Prefix all storage paths with the authenticated user's JWT subject
- Local filesystem implementation (v1)
### Non-Functional Requirements
#### 1. Performance (Primary Goal)
- Optimize for thousands of small files
- Minimize per-file overhead
- Avoid one-transaction-per-file patterns
- Batch metadata operations where possible
- Target significantly faster small-file uploads than Nextcloud
#### 2. Concurrency Model
- Use Java virtual threads (Project Loom) for request handling
- Thread-per-request model with blocking I/O
- Bounded resources:
	- DB connection pool
	- filesystem throughput
- Avoid thread pools for request handling
#### 3. Scalability
- Single-node optimized (initially)
- Clean separation between:
	- metadata (DB)
	- files (filesystem storage)
- Allow future horizontal scaling via:
	- stateless app instances
	- external/shared filesystem or object-storage adapter
#### 4. Consistency Model
- Strong consistency for metadata (Postgres transactions)
- File writes are:
	- write → finalize → publish
- No partial visibility of uploaded files
#### 5. Storage Efficiency
- Optional deduplication or integrity checks via checksum
#### 8. Extensibility
- Pluggable file storage interface
- Clear separation of concerns:
	- API layer
	- service layer
	- storage layer
- Future support:
	- object storage adapter (S3/MinIO)
	- background workers (indexing, previews)
